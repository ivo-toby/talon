# Browser voice

Talon can expose an opt-in browser voice session at `/voice/`. The browser
uses WebRTC for the live audio path. Talon keeps authentication, policy, the
session lifecycle, and any delegated backend work on the daemon; SIP and
other transports are not currently supported.

## Requirements

- A persona whose configured provider is enabled. Voice backend work uses that
  persona's normal model and queue, including its provider's normal OAuth and
  native-tool restrictions.
- A voice access token and, when the live provider requires one, a live API
  key. Keep both in environment variables referenced by `auth.providers`.
- HTTPS for a browser reached through a network. Local loopback testing can
  use HTTP. The listener defaults to loopback; when a reverse proxy runs in a
  different VM, container, or network namespace, set `voice.host` to a
  reachable interface address (or `0.0.0.0`) and restrict network access.
- A reverse proxy that preserves the public `Host` and `Origin` headers and
  sends `X-Forwarded-Proto: https`. Talon uses that header when deciding
  whether to mark the authentication cookies `Secure` and when checking the
  same-origin read path.

## Configuration

The feature is disabled by default. This example contains no secret values:

```yaml
auth:
  providers:
    voice:
      apiKey: ${TALON_VOICE_ACCESS_TOKEN}
    openai:
      apiKey: ${OPENAI_API_KEY}

voice:
  enabled: true
  host: 127.0.0.1
  port: 8787
  publicHost: voice.example.com
  accessTokenRef: voice
  liveApiKeyRef: openai
  # provider: openai-compatible  # deprecated compatibility field; persona provider is authoritative
  model: gpt-live-1
  persona: assistant
  voice: marin
  # usdPerMinute: 0.00 # replace with a current provider rate; omitted means unavailable
  allowedOrigins:
    - https://voice.example.com
  allowedTransportTypes:
    - webrtc
  allowedToolNames: []
  allowedMcpServerNames: []
```

`voice.persona` selects an existing normal persona. Its backend model, ordinary
tools, skills, and configured MCP servers are used through the same
`AgentRunner` path as text work. The selected persona's configured provider (or
the agent-runner default) is authoritative and must be enabled; the provider's
normal OAuth and native-tool restrictions remain in force. The persona's
`model` is the backend model. `voice.model` is the separate live voice model
sent to the live provider. Approval-gated capabilities are unavailable because
voice has no interactive approval channel, and unproven MCP servers fail
closed.

The old `voice.allowedToolNames` and `voice.allowedMcpServerNames` fields are
deprecated compatibility fields and are ignored. Do not use them to grant
voice access. The selected persona's normal capability policy is authoritative.

When `voice.enabled` is true, `browser-voice` is reserved for Talon's internal
voice channel. Startup rejects a conflicting ordinary channel configuration and
does not overwrite an existing non-voice `browser-voice` database row.

`publicHost` adds `https://<publicHost>` to the allowed origins and documents
the external URL. It does not change the listener address. Keep the default
loopback `host` when the proxy shares the daemon's network namespace; for a
remote proxy, configure `host` to the address that proxy can reach. Origin,
authentication, and CSRF checks still apply to every listener address.

## Login and session flow

Open `https://voice.example.com/voice/` after the daemon and proxy are ready.
The browser submits the access token once to `POST /voice/login`. Talon
exchanges it for an expiring, opaque `HttpOnly` session cookie and a CSRF
cookie. The access token is not returned to the browser API, included in
session status, or written to logs. Mutating requests use the CSRF cookie and
`X-CSRF-Token` header; an unauthenticated request cannot create a session or
reach the queue/provider path.

The HTTP boundary exposes these routes:

| Route                               | Purpose                                                    |
| ----------------------------------- | ---------------------------------------------------------- |
| `GET /voice/healthz`                | Unauthenticated health check                               |
| `POST /voice/login`                 | Exchange the configured token for browser cookies          |
| `POST /voice/logout`                | Revoke the browser login and close its active sessions     |
| `POST /voice/sessions`              | Create an authenticated WebRTC session                     |
| `GET /voice/sessions/:id`           | Read retained session, delegation, output, and usage state |
| `GET /voice/sessions/:id/events`    | Subscribe to authenticated status events with SSE          |
| `POST /voice/sessions/:id/close`    | Hang up or close a session                                 |
| `POST /voice/sessions/:id/playback` | Report output playback state                               |

The browser sends a transport offer. The server chooses the configured persona,
provider, live model, output voice, tools, and MCP policy from the current
login. Provider events become bounded context snapshots, then durable voice
delegations on the ordinary queue and `AgentRunner` path.

## Lifecycle and limits

Talon stores session, delegation, bounded prompt fragments, policy, usage, and
finalization state in SQLite. The owner/persona pair uses one durable voice
thread across calls. Prompt history is bounded by
`DEFAULT_VOICE_HISTORY_ROWS` and `DEFAULT_VOICE_HISTORY_CHARACTERS`; a
restart recovers that history without replaying completed queue work. A
transcript correction supersedes the earlier context before queue claim; it
must not replay an already claimed delegation. Older calls and messages from
other channels are not imported automatically.
Policy is checked again before execution, so a revoked login or changed
generation/policy prevents new backend work. A hangup skips unclaimed work and
retains the result of work that was already claimed or running. Output state
records execution, delivery, provider acknowledgement, and browser playback
separately, so a late result remains inspectable after the call is closed.

The configured session lifetime, concurrent-session limit, and session-creation
rate limit are bounded by the `voice` settings. Retained voice rows do not
contain raw audio. The current runtime has no automatic voice-row TTL cleanup;
operators should include the SQLite voice tables in their local data retention
and backup policy.

## Cost and privacy

The live provider receives the audio and live transcript data required for the
call. Provider-side cloud retention and deletion are controlled by that
provider's account and API settings, not by Talon. Talon does not claim to
delete or control provider-side retention.

Local SQLite stores bounded prompt snapshots and output text needed for session
recovery and audit. There is no automatic TTL cleanup for durable voice rows;
include the SQLite voice tables in the operator's retention and backup policy.
Raw audio is not persisted in the voice schema. Set
`voice.usdPerMinute` only when the operator has a current provider rate; it is
optional and has no default. With a configured rate, Talon estimates voice cost
from cumulative provider-reported seconds. Final provider usage does not
confirm billing, so that estimate remains `estimated`; when that rate has
known usage but an incomplete close, the status is `incomplete`, and no
configured rate is `unavailable`.
Talon never fabricates a voice dollar amount from token totals. Backend cost is
reported only from the AgentRunner run accounting and is kept separate. Voice
prompt and output content is redacted from the Langfuse voice observation path,
while local database and operational logs may still contain sensitive bounded
text.

## Validation boundaries

The repository includes an offline integration harness using actual daemon
bootstrap, `BrowserVoiceServer`, cookie/CSRF authentication, SQLite voice
migrations, `VoiceSessionService`, the durable bridge, queue, channel
connector, OAuth resolver, and `AgentRunner`; only the live provider and
external backend command are fake. It covers normal persona/provider selection,
permitted `channel_send`, approval denial including a direct bridge attempt,
shared-thread recovery across restart, and no old-work replay. Browser UI
checks cover login, denied microphone handling, mute/hangup/restart, retained
closed sessions, a 390px viewport, and console errors against integrated build
assets.

Those checks do not establish a physical iPhone/Safari call or a paid live
provider call. Run those separately before treating external-provider or
mobile acceptance as complete.
