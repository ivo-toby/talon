# Talon WDD Constitution

## Status and authority

Draft migration from the legacy text-only constitution (previously dated 2026-07-10) to the installed wddctl workflow. This draft is not ratified. Ivo must approve the exact constitution and config before ratification. AGENTS.md remains authoritative; authorization to configure WDD is not authorization to implement the voice feature, create/change tests, start services, access secrets, push, or merge.

## Scope and artifacts

WDD coordinates Talon development and is not a Talon runtime dependency. The controller owns state.json and generated state projections; agents must not edit them manually. config.json contains machine-consumed policy; this constitution explains it.

Use wddctl epic new for future active epic namespaces, the intake/spec/design/plan gates, plan preview and dry-run, then apply only the approved plan. Workers execute task briefs in isolated worktrees. The controller drives wddctl next and records review, verification and reconciliation evidence through the CLI. Existing templates and .wdd/work artifacts are legacy references, not an active controller state.

The existing EPIC-browservoice folder is an unactivated planning draft. After governance approval, import its reviewed content into a controller-created epic namespace without deleting the draft or hand-editing state. Scope activation and worker dispatch require approval of the voice plan and resolution of its explicit permission prerequisites.

## Branching

- Target branch: main.
- Epic/base naming: epic/{scope-slug}.
- Task naming: task/{task-id}, generated by the controller.
- Worktrees: .worktrees inside the repository, already gitignored.
- Planning/configuration changes stay on a feature branch.
- Task integration targets the epic branch; final integration targets main.
- No destructive Git operations without explicit approval. Never amend a pushed commit or skip a hook.

## Verification

- Node.js 24+ and npm/package-lock.json are the supported runtime/tooling.
- Configured baseline commands, in order: npm run lint; npx tsc --noEmit; npm run build.
- For source changes, run relevant existing and approved new targeted Vitest tests after typechecking and before build. Each task brief must name its concrete test command; the baseline commands alone do not constitute complete verification.
- Full npm test is slow and requires Ivo's approval. Do not run a guessed Python test command.
- Creating or changing tests requires approval under the supplied global instructions. Once authorized, tests should exercise meaningful behavior and regressions.
- Check user-visible behavior after the build. Runtime smoke follows .agents/skills/run-talon-smoke/SKILL.md; starting services and credential use require approval.
- Documentation-only tasks use parse/reference/whitespace checks; mark runtime checks not applicable with a reason rather than fabricate success.
- Record commands actually run, results/counts and limitations. A passing check is not human acceptance or authorization.

## Review policy

- Default review policy: always.
- No mandatory review before each commit. WDD task/spec reviews are separate workflow gates, performed with GPT-6.1 Sol at xhigh reasoning.
- P1/P2 findings block integration. P3 findings are documented and tracked when relevant.
- Review all changes against the spec, task scope, security boundaries and documentation. Resolve fixed or invalid PR comments with the fixing commit or rationale when PR work is explicitly authorized.
- High risk includes authorization, persistence/migrations, provider sessions, public contracts, runtime lifecycle and externally visible actions.

## Models and dispatch

Planning uses the invoking harness default (null in config). Implementation, including high-risk tasks, uses gpt-5.6-luna with reasoning effort max. PR authoring and updates use gpt-6.1-sol with reasoning effort xhigh. WDD review and specification review also use gpt-6.1-sol with reasoning effort xhigh; these are not per-commit gates.

The installed wddctl model fields select model names only; they do not configure reasoning effort. For agent-harness dispatch, explicitly pass model gpt-5.6-luna / reasoning_effort max for implementation and model gpt-6.1-sol / reasoning_effort xhigh for PR work and WDD reviews, with a fresh context when required by the harness. Record the actual model and effort in task evidence. A future CLI runner must pass and validate equivalent settings before use. Do not claim config.json alone enforces reasoning effort. If a required combination is unavailable, report it before substituting.

No shell runner is configured automatically. Use the available agent harness for dispatch and preserve model selection. Register and probe a runner only if that execution method is subsequently selected. Workers own a bounded set of paths and preserve others' work.

## Merge policy

- Surface: local by default. Publishing branches/PRs requires separate explicit approval; change the surface before an approved PR workflow.
- Mode: human. No automatic task or final merges; obtain explicit go-ahead, then use the controller's integration verbs.
- Reconcile after every merge.
- Maximum concurrency: 3. Dependencies and overlapping conflict domains may reduce concurrency.
- Never equate completed tasks or green tests with final epic completion. Check final integration state separately.

## Documentation and scope discipline

Follow Talon's Result-based error handling, capability boundaries and existing patterns. Keep changes local to the assigned task. Feature work updates README, relevant .agents/skills and AGENTS.md when architecture/conventions change. No secrets, production data, ignored runtime configs, node_modules or dist in planning artifacts.

## Governance

Initial ratification of this migrated controller configuration uses wddctl constitution ratify with Ivo's explicit approval and the current exact-content fingerprint. Later policy edits require explicit re-approval and wddctl constitution amend. Never self-ratify from detected defaults. The CLI owns the ratification record; prose status does not override controller state.
